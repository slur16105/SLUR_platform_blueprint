## 1. 무엇이 잘못됐나

Slur의 원래 의도는 **구매자 화면 = 모바일 퍼스트 반응형 웹 + 하이브리드 앱(웹앱)** 이었으나,
실제로는 **Flutter 네이티브 앱**으로 구현됐다.

**분기 지점: 프로덕트 브리프 (2026-07-14)**

```
brief.md:38  구매자 (Flutter, 모바일 퍼스트): 로그인 · 회원가입 · 상품목록 · ...
```

"모바일 퍼스트"가 **"모바일 퍼스트 반응형 웹"이 아니라 "네이티브 모바일 앱 우선"** 으로 해석되어
Flutter에 붙었다. 이 표현이 확인 없이 브리프에서 굳었고, PRD(`prd.md:14, 27, 37`)로 그대로
복사된 뒤 Epic 1~6 전체가 그 전제 위에서 구현됐다. 중간에 재확인 절차가 없었던 것이 원인.

## 4. 미결 의사결정 (Slur 답변 필요)

착수 전 반드시 확정. 되돌리기 비용이 큰 갈림길.

### Q1. 하이브리드 앱 방식
- **(A) PWA** — Next.js 반응형 웹 + manifest + service worker. 스토어 심사 없이 홈화면 설치·오프라인 캐시.
  가장 빠르고 유지비 0. 단점: iOS 푸시·결제 제약.
- **(B) WebView 래퍼 (Capacitor)** — 같은 반응형 웹을 감싸 Play스토어 APK 출시.
  네이티브 푸시·카메라 접근 가능. 스토어 심사·빌드 파이프라인 추가 부담.
- **(C) PWA 먼저, 래퍼는 나중** — v1은 PWA로 완주, 스토어 출시가 실제로 필요해지는 시점에 Capacitor 덧씌움.
  웹 코드가 동일해 나중 전환해도 손실 없음.

### Q2. 기존 Flutter 앱 처리
- **(A) 보관 후 제거** — `apps/mobile`을 별도 브랜치·태그로 남기고 main에서 걷어냄.
  구현된 화면·플로우는 반응형 웹 재구축의 참고 자료로 활용.
- **(B) 당분간 병존** — Flutter 유지 + 웹 구매자 화면 추가. 두 클라이언트 동시 유지는 완주 목표에 부담.
- **(C) 즉시 삭제** — 참고 자료도 남기지 않음.

### Q3. 디자인 시안 범위
- **(A) 핵심 3화면 × 3안** — 상품목록·상품상세·장바구니를 서로 다른 톤 3안으로.
  방향 결정에 충분하고 빠름. 선택 후 나머지는 확정된 톤으로 전개.
- **(B) 구매자 전 8화면 × 2안** — 완성도 높지만 시간·토큰 소모 큼.
- **(C) 상품목록 1화면 × 4안** — 얼굴이 되는 화면 하나만 폭넓게 탐색해 톤을 먼저 확정.
