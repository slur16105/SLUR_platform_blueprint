## 발견 1 — 우편번호 검색·도서산간 판정이 착지하지 않았다 (a, 높음)

- **PRD 근거**: FR-16 "배송지 입력(우편번호 검색 — **검색 제공자는 아키텍처 단계에서 결정**)", FR-17 "배송지 우편번호로 도서산간 여부 자동 판정". 부록 기술 노트: "우체국/택배사 공개 우편번호 목록 기반 **판정 테이블**".
- **스파인 현황**: 우편번호 검색 제공자(카카오 주소검색 등) 결정 없음. 도서산간 판정 테이블은 승인 ERD에 없고, 어느 도메인(orders? sellers? core?) 소관인지도 없음. Deferred에도 없음.
- **왜 문제인가**: PRD가 명시적으로 아키텍처 단계로 넘긴 유일한 결정 사항인데, 스파인이 결정도 유예 선언도 하지 않았다. 이대로면 구현 시점에 임의 결정되고, 판정 테이블 추가는 AD-9(스키마 승인 게이트)에 걸려 재승인 왕복이 발생한다.
- **제안**: 제공자 결정(예: 클라이언트 측 우편번호 검색 위젯 + FastAPI 측 도서산간 판정)을 컨벤션 표에 1행 추가하고, 판정 테이블(`remote_area_zipcodes` 류)을 ERD에 반영하거나 최소한 Deferred에 재개 조건과 함께 명시.

## 발견 2 — 자동취소 배치의 실행 주체가 없다 (a, 중간)

- **PRD 근거**: FR-18 "주문 후 3일 내 미입금 → 자동취소" + FR-11 취소 시 재고 복원.
- **스파인 현황**: AD-3이 "자동취소 배치"를 전이 함수의 호출자 중 하나로 **호명은** 하지만, 그 배치가 어디서 도는지는 배포 토폴로지(Railway cron? FastAPI 내장 스케줄러? 별도 워커?)에도, Deferred에도 없다. Alembic pre-deploy는 명시하면서 유일한 시간 기반 프로세스는 빠졌다.
- **왜 문제인가**: 스파인의 배포 토폴로지가 시스템의 프로세스 전체를 그린다고 읽히는 문서인데, 여기 없는 상시 프로세스가 하나 존재한다. 구현자가 임의로 선택하면 배포 단위·장애 지점이 조용히 늘어난다.
- **제안**: 토폴로지에 실행 방식 1줄 확정(예: Railway cron이 FastAPI의 관리용 엔드포인트/커맨드 호출) 또는 Deferred에 명시.

## 발견 3 — 구매자 취소 규칙의 3자 충돌 (b, 중간)

- **PRD 근거**: FR-18 "구매자 자유취소: **배송준비 진입 전까지**" + FR-15 배송 상태는 판매자별(하위주문) **독립 전이**.
- **스파인 현황**: AD-6 "구매자 전체 취소는 전 라인 일괄 취소로 구현한다. **부분(라인) 취소는 관리자만** 수행한다."
- **충돌 시나리오**: 판매자 A 하위주문이 `preparing` 진입, 판매자 B는 아직 `paid`. 이때 구매자는 — A가 이미 배송준비라 전체 취소 불가, 부분 취소는 관리자 전용이라 B만 취소도 불가. 결과적으로 PRD가 부여한 "배송준비 전 자유취소" 권리가 B 하위주문에 대해 소멸한다. PRD는 취소 창을 상태 기준으로만 정의했지 "전 판매자가 동시에 배송준비 전이어야"라는 조건을 단 적이 없다.
- **제안**: 둘 중 하나로 확정 필요 — (i) 구매자 취소 단위를 하위주문으로 완화(AD-6 수정), 또는 (ii) "혼합 상태 주문의 구매자 취소는 관리자 경유"를 의도된 축소로 스파인에 명문화하고 PRD와 정합 확인(Slur 판단 사항).

## 발견 4 — 2차 목표 "블루프린트 추출"이 설계 원칙에서 유실 (c, 낮음~중간)

- **PRD 근거**: §2 목표 2 "완성 후 범용 커머스 플랫폼 블루프린트를 추출한다". 부록: Supabase 풀스택 기각 사유에 "**블루프린트 추출 관점에서도 로직이 한 곳에 있어야 추출이 쉬움**" — 즉 추출 가능성이 이미 아키텍처 결정의 근거로 작동한 조용한 제약이다.
- **스파인 현황**: AD-1의 Prevents에도, 어떤 규칙에도 "추출 가능성/범용성"이 등장하지 않는다. FR-34의 "카테고리 하드코딩 금지" 정신(SLUR 고유 값을 코드에 새기지 않기)이 일반 규칙으로 승격되지 않았다.
- **왜 문제인가**: 규칙이 없으면 구현 과정에서 브랜드명·정책 상수·문구가 코드 전반에 스며들고, v1 완주 후 추출 비용이 커진다. 스파인이 이 제약을 침묵하면 하위 문서는 이를 모른 채 진행한다.
- **제안**: 가벼운 컨벤션 1행이면 충분 — 예: "SLUR 고유 값(브랜드명·계좌·정책 상수·고지 문구)은 settings/설정·환경변수로 외재화, 도메인 코드에 하드코딩 금지".

## 발견 5 — refresh token 저장 구조가 승인 ERD에 없다 (a, 낮음)

- **PRD 근거**: NFR-2 access + refresh token 방식 (스파인 컨벤션도 "access 30분 + refresh" 채택).
- **스파인 현황**: refresh token의 저장 위치·폐기(로그아웃·탈취 대응) 구조가 없다. 서버 저장형이라면 테이블이 필요한데 승인 ERD(2026-07-15)에 해당 테이블이 없다 — "컬럼 상세는 마이그레이션에서"로 덮이는 수준(컬럼)이 아니라 테이블 단위 누락이라 AD-9 게이트상 재승인이 필요해진다.
- **제안**: stateless(서명 검증만) vs 서버 저장(폐기 가능) 중 택일을 컨벤션에 1줄로 확정하고, 서버 저장이면 ERD에 테이블 반영.
