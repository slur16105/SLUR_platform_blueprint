# Good-Spine 체크리스트 리뷰 — ARCHITECTURE-SPINE (SLUR 커머스 플랫폼 1호)

심각도 기준: **다운스트림 빌더(도메인 모듈·클라이언트 구현자)가 서로 갈라질 위험**.

- HIGH — 스파인이 침묵/모순하여 빌더 둘이 서로 다른 구조를 만들 것이 거의 확실
- MEDIUM — 해석 여지가 있어 갈라질 수 있으나, 갈라져도 수렴 비용이 국소적
- LOW — 정보 누락·표기 불일치. 갈라짐보다는 혼란 유발

## 종합 판정: 조건부 통과 (REVISE)

스파인의 핵심 — AD-1~9의 불변식, ERD 시드, 전이표 단일 통로, 조건부 UPDATE, 라인 레벨 취소 — 은 리서치 근거와 Slur 승인 이력(.memlog)에 단단히 결박되어 있고 집행 가능하다. 그러나 **운영 envelope가 거의 전부 침묵**하고(H-1), **AD-2 의존 그래프가 PRD가 요구하는 실제 호출을 담지 못하며**(H-2), **PRD가 명시적으로 아키텍처 단계에 위임한 결정 하나가 처리되지 않았다**(H-3). 세 건 모두 첫 스프린트에서 빌더가 즉시 부딪히는 지점이므로, 배포 전 스파인 수정을 권고한다.

## HIGH

### H-1. 운영 envelope 침묵 — 이 고도가 소유한 차원이 결정/유예/열린질문 어디에도 없다 (체크 6)

스파인의 Deferred 표는 CI/CD 상세와 백업·모니터링만 유예했다. 그 사이에 있는 다음 차원들은 **결정도, 유예도, 열린 질문도 아닌 상태**다:

1. **자동취소 배치(3일 미입금, FR-18·OQ-2)의 실행 방식.** AD-3은 "자동취소 배치"를 전이 함수의 호출자로 명명하지만, 그 배치가 *무엇으로 도는지* — FastAPI 프로세스 내 스케줄러(APScheduler)인지, Railway cron 서비스인지, pg_cron인지 — 는 어디에도 없다. 이것은 배포 토폴로지를 바꾸는 결정이다(별도 서비스면 Railway 서비스 3개, 인프로세스면 다중 인스턴스 시 중복 실행 문제). 빌더마다 다른 답을 낼 것이 확실하다.
2. **환경 분리(dev/prod).** Railway 환경 2개인지, Supabase 프로젝트를 분리하는지(비용 발생 → memlog의 코칭 규칙상 Slur 승인 대상), Alembic 마이그레이션이 어느 환경에서 먼저 도는지 — 전부 침묵.
3. **시크릿 관리.** JWT 서명 키, 카카오 OAuth 키, DB URL, Storage 서비스 키의 보관·주입 방식(Railway 변수? .env 규약?)이 없다. AD-1이 "FastAPI가 유일한 문지기"라면 문지기의 열쇠 관리가 스파인 차원이다.
4. **로컬 개발 환경.** 로컬 Postgres(docker-compose? Supabase CLI local?)와 Storage 대역을 무엇으로 쓰는지 규약이 없다. 두 빌더가 서로 다른 로컬 기반 위에서 작업하면 마이그레이션·시드 데이터부터 갈라진다.

**권고**: 위 4건을 각각 결정(AD 또는 컨벤션 행 추가) 또는 재개 조건 있는 Deferred로 승격. 특히 1번(배치 실행 방식)은 배포 토폴로지에 닿으므로 결정이 필요하고, 비용에 닿는 2번은 memlog 규칙대로 Slur 선택지로 올려야 한다.

### H-2. AD-2 허용 방향 그래프에 PRD가 강제하는 엣지 2개가 없다 (체크 1, 2)

AD-2의 Rule은 "허용 방향" 그래프를 집행 규범으로 선언했다. 그런데:

- **orders → sellers 누락.** 주문서의 배송비 계산(FR-16, FR-17)은 판매자별 배송비 설정을 읽어야 하고, 배송비 설정은 패러다임 트리가 명시적으로 `sellers/`에 배치했다("입점 신청·승인, 판매자 프로필, **배송비 설정**"). 또 ERD에서 `sellers ||--o{ sub_orders`이므로 주문 생성이 seller를 참조한다. 현재 그래프대로면 orders는 sellers의 service를 호출할 수 없다 — 빌더는 (a) 그래프를 위반하거나, (b) 배송비 설정을 products 경유로 우회 복제하거나, (c) 배송비 로직을 orders에 중복 구현하는 세 갈래로 갈라진다.
- **admin → auth 누락.** FR-30(회원 관리: 목록·검색·상세)은 admin이 users를 조회해야 하는데, users는 `auth/` 소유다. 그래프상 admin → auth 경로가 없다.

**권고**: 그래프에 `orders --> sellers`, `admin --> auth` 추가. 추가하는 김에 "이 그래프는 전이적 축약이 아니라 직접 호출 허용 목록 전체"임을 Rule에 한 줄 명시하면 집행 가능성이 확정된다(예: import-linter 계약으로 그대로 옮길 수 있는 형태).

### H-3. 우편번호 검색 제공자 + 도서산간 판정 — PRD가 아키텍처 단계에 위임했는데 미처리 (체크 1, 5, 6)

FR-16은 "우편번호 검색 — **검색 제공자는 아키텍처 단계에서 결정**"이라고 명시적으로 이 문서에 결정을 위임했고, FR-17은 도서산간 자동 판정을 요구한다(addendum은 우체국/택배사 공개 목록 기반 판정 테이블까지 제시). 스파인에는 제공자 결정도, 판정 테이블의 소속 도메인도, ERD 엔터티도, Deferred 항목도 없다. Capability Map의 F4 행이 FR-16~17을 명목상 덮고 있을 뿐이다. 클라이언트(Flutter/Next.js 양쪽) 통합 방식이 제공자에 따라 완전히 달라지는 분기점이다.

**권고**: 제공자 결정(예: Daum/카카오 우편번호 서비스 — 순수 기술 갈림길이므로 memlog 규칙상 AI 결정+기록 대상) + 도서산간 판정 테이블의 도메인 배치(orders 또는 core)를 결정하거나, 명시적 재개 조건과 함께 Deferred로 넣을 것.

## MEDIUM

### M-1. AD-3 전이표가 관장하는 상태 기계의 범위 모호 — AD-6과의 접합부 (체크 2)

AD-6/ERD에 따르면 상태는 세 층이다: `orders`(결제: 입금대기→결제완료), `sub_orders`(판매자별 배송: 배송준비→배송중→배송완료), `order_items`(라인 취소). AD-3은 "주문 상태 전이는 전이표 + **단일 함수 하나**"라고 하는데, 이 단일 함수가 세 층을 모두 관장하는지(층을 인자로 받는 하나의 표?), 층마다 전이표·함수가 따로인지(그럼 "단일"의 의미는 층 내 단일?) 해석이 갈린다. 취소는 상태 전이이자 재고 복원(AD-4)·cancellations 기록(AD-6)을 동반하므로, 이 접합부의 해석 차이는 트랜잭션 경계 설계까지 번진다. **권고**: AD-3에 한 문장 추가 — 전이표의 행이 (레벨, 현재 상태, 목표 상태, 허용 역할)임을 명시하거나, 층별 전이표 3개+공통 검사 함수 1개 구조임을 못 박을 것.

### M-2. 웹 클라이언트의 토큰 보관·전달 방식 미결 (체크 1, 3)

컨벤션은 "access 30분 + refresh, 두 클라이언트 공통"까지만 고정했다. Next.js에서 토큰을 어디 두는지(httpOnly 쿠키 vs 브라우저 스토리지+Bearer 헤더)는 FastAPI 쪽 API 계약(쿠키 수신 여부, CSRF 대응)까지 바꾸는 분기점인데, Deferred의 "프론트 상세 폴더 구조" 항목은 이를 덮지 않는다 — **폴더 구조가 아니라 인증 계약이므로 유예 항목 사이에 숨은 갈라짐**이다(체크 3의 적중 사례). 배포 다이어그램도 브라우저→WEB→API 경로만 보여 브라우저가 API를 직접 치는지조차 확정하지 않는다. **권고**: 인증 흐름 컨벤션 행에 토큰 보관 위치와 브라우저→API 직접 호출 여부를 한 줄로 확정.

## LOW

### L-1. `settings` 테이블이 ERD 다이어그램에 없음 (체크 7 인접)

본문 불릿과 memlog("16개 테이블")에는 있으나 mermaid erDiagram에는 15개 엔터티만 있다. 관계 없는 독립 테이블도 엔터티 선언은 가능하다. Slur가 승인한 ERD의 시각 표현과 텍스트가 어긋난 상태.

### L-2. refresh token의 서버측 취급 미명시

저장(DB 테이블? 무상태?)·회전·로그아웃 시 폐기 여부가 없다. ERD에 토큰 테이블이 없으므로 무상태로 읽히지만 명시가 아니다. 컬럼 상세가 AD-9 게이트로 유예된 것과 결이 같아 LOW로 둔다.

### L-3. Flutter 3.44 과도기 리스크가 스파인에 미반영

research-stack-versions.md §4가 경고한 Material/Cupertino SDK 분리 과도기·Impeller 강제는 첫 Flutter 셋업에서 부딪히는 사안인데 스파인 Stack 표는 버전만 옮겼다. 정보성 각주 한 줄이면 충분.
