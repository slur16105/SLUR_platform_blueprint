# SLUR 커머스 플랫폼 1호 — PRD

> 입력: 프로덕트 브리프(2026-07-14, final) + Slur와의 섹션별 논의(결정 이력은 `.memlog.md`, 리서치는 `research-*.md`). 독자는 Slur와 AI. 추정으로 채운 항목은 `[ASSUMPTION]` 표시.

## 1. 개요

운영자가 판매자를 직접 선별·초청하는 **큐레이션형 디자인 편집숍 마켓플레이스** (통신판매중개자 모델). 구매자는 Flutter 모바일 앱(**Android 먼저 출시, iOS는 이후**)을, 판매자·관리자는 Next.js PC 웹(단일 앱, Role 분기)을 쓴다. 백엔드는 FastAPI가 모든 권한·비즈니스 로직을 소유한다.

## 2. 목표와 성공 기준

1. **1차 목표: 실서비스를 끝까지 만들어 운영해본다.** 매출·사용자 수는 1차 성공 조건이 아니다.
2. **2차 목표: 완성 후 범용 커머스 플랫폼 블루프린트를 추출한다.** 이 PRD와 여기서 파생되는 산출물이 다음 플랫폼의 시작 문서가 된다. (원래 이 프로젝트의 출발 아이디어였고, "백지에서 설계"가 아니라 "실물에서 추출"로 방향 전환한 결과다. 추출할 산출물 목록은 v1 완주 시점에 확정한다.)

**판정 기준(counter-metric)**: 기능 추가 욕심이 생기면 "완주에 기여하는가"로 판정한다. 로그인 제공자 수, 관리 기능의 정교함 등은 완주에 기여하지 않는다 — 실제로 이 기준으로 네이버 로그인·제재 기능·상품 검수를 v1에서 제외했다.

## 3. 사용자와 역할

| 사용자 | 누구 | 접점 |
|---|---|---|
| 구매자 | 여성 비중 높음 | Flutter 앱 (Android 먼저) |
| 판매자 | 소상공인 디자인 브랜드/작가 (초청·승인제, 1차 오픈 5~10팀) | Next.js PC 웹 |
| 관리자 | 운영자(Slur 측) | Next.js PC 웹 (판매자와 동일 앱, Role 분기) |

**계정 모델: 단일 계정 + 역할(Role).** 가입하면 누구나 구매자. 입점 승인 시 같은 계정에 판매자 역할이 추가된다(네이버·유튜브 채널 모델). 관리자는 운영자 계정에만 부여. 한 계정이 여러 역할을 동시에 가질 수 있고, Flutter 앱과 PC 웹에 동일 자격증명으로 로그인한다. 역할 판정·권한 분기는 전부 FastAPI(RBAC)가 소유한다.

## 4. 범위

### v1 기준선 (브리프의 화면 목록 = 기준선, 이후 논의로 구체화)

- **구매자 (Flutter)**: 로그인 · 회원가입 · 상품목록 · 상품상세 · 장바구니 · 주문서(배송지 입력) · 주문내역 · 주문상세
- **판매자·관리자 (Next.js)**: 입점 신청 · 판매자 대시보드 · 상품관리(옵션 입력 표) · 주문관리 · 관리자 화면(입점 승인, 회원/판매자/상품/주문 관리, 입금 확인)
- **공통**: 이용약관 · 개인정보처리방침 · 푸터(사업자 정보 + 통신판매중개자 고지)

### 결제 단계 구분 (v1의 핵심 경계)

- **v1 개발·내부 테스트: 무통장입금.** 관리자가 수동으로 입금 확인. PG 전에 실제 외부 구매자를 받지 않으므로 구매안전서비스(에스크로)·입금계좌·지급대행 규제 문제는 v1 범위에서 발생하지 않는다.
- **실서비스 오픈 게이트(오픈의 선행 조건): PG 연동.** 이때 `입금대기→결제완료`가 PG 자동 승인으로 대체된다. 수수료·정산·배송비 지원 설계도 이 시점에 한 묶음으로 재논의한다. PG 비용 현황은 `research-pg.md`.

### v1 제외 (금지가 아니라 "필요 미확인" — 필요 확인 시 추가)

리뷰 · 검색 · 알림 · 찜/위시리스트 · 쿠폰/프로모션 · 상품 검수 · 회원 제재 · 반품/교환 워크플로 · 정산 · iOS 출시 · 네이버/구글 로그인 · 직접입력형 옵션 · 예약 재고

## 5. 기능 요구사항

### F1. 계정·인증

- **FR-1** 이메일+비밀번호 회원가입·로그인. 비밀번호는 Argon2id 해시 저장 (당초 bcrypt — 아키텍처 검증 시 OWASP 현행 권고로 교체, Slur 승인 2026-07-15).
- **FR-2** 카카오 로그인 (구매자 앱·PC 웹 모두). 카카오는 신원 확인 수단일 뿐, 토큰 발급은 FastAPI 자체 JWT로 한다. 소셜 인증 구조는 제공자 추가(네이버·구글)가 쉬운 범용 OAuth 형태로 설계한다.
- **FR-3** 단일 계정 다중 역할(구매자/판매자/관리자). 모든 API의 권한 판정은 FastAPI RBAC.
- **FR-4** `[ASSUMPTION]` 이메일 가입 시 수집 항목은 이메일·비밀번호·이름(또는 닉네임)·(선택)휴대폰번호 최소 구성. 이메일 인증(본인 확인 메일)은 v1 생략.

### F2. 입점

**입점 승인은 관리 기능이 아니라 브랜드 전략의 도구다** (브리프 승계) — 무분별하게 받지 않고 운영자가 선별해 플랫폼의 결을 유지한다. 아래 FR들이 기능적으로 단순한 이유는 전략이 단순해서가 아니라, 전략적 판단(선별)이 시스템 밖(초청)에서 일어나기 때문이다.

- **FR-5** 입점 신청 폼. 심사는 초청 전 오프라인에서 끝나므로 폼은 온보딩 서류 — 필요 최소 정보만:
  - 법정 필수: 상호, 대표자명, 사업자등록번호, 통신판매업 신고번호, 사업장 주소, 연락처 (근거: 전자상거래법 — 중개 플랫폼은 판매자 신원정보를 구매자에게 청약 전 제공할 의무, `research-market.md` §4)
  - 운영 필수: 브랜드명(노출용), 브랜드 소개
  - v1 보류: 정산 계좌 (정산은 PG 도입 시점에 설계)
- **FR-6** 신청 페이지는 상시 존재. 초기엔 초청 브랜드에게만 링크 공유, 공개 전환은 운영 정책 변경만으로 가능 (승인 게이트는 항상 유지).
- **FR-7** 관리자 승인/반려 (반려 사유 입력). 승인 시 해당 계정에 판매자 역할 부여, 즉시 상품 등록 가능. 승인 대기 중 신청자에게 "심사 중" 상태 표시.

### F3. 상품·옵션·재고

업계 표준 조합형(variant) 모델의 축소판. 벤치마킹: `research-options-inventory.md` (스마트스토어·카페24·아임웹·Shopify·Medusa·Saleor 공통 구조).

- **FR-8** 상품 등록: 상품명, 가격, 설명, 이미지(Supabase Storage), 옵션. **검수 단계 없음 — 등록 즉시 노출** (초청제가 품질 게이트).
- **FR-9** 옵션: 축 최대 2개(예: 색상×사이즈) → 조합 행 자동 생성 → 행마다 [옵션값 | 추가금액 | 재고수량 | 판매상태]를 표(그리드)에서 입력. 옵션 없는 상품은 내부적으로 조합 1개로 처리.
- **FR-10** 재고: 조합별 수량 관리. 0이 되면 자동 품절 + 판매자 수동 품절 토글 병행. 품절 옵션은 선택 목록에서 "품절" 표기로 비활성 (숨기지 않음).
- **FR-11** 재고 차감은 주문 생성 시점 (동시 주문에도 음수 재고가 발생하지 않아야 한다). 장바구니 담기 시점 차감은 하지 않는다. **주문이 취소되면(미입금 자동취소·구매자 자유취소·관리자 강제 취소 모두) 차감된 조합 재고를 복원한다.**
- **FR-12** `[ASSUMPTION]` 상품 상태는 판매중/품절/숨김 3단계 (아임웹 모델). 판매자가 직접 전환.
- **FR-13** `[ASSUMPTION]` 상품 이미지는 대표 1장 + 추가 N장(상한 10장), 상세 설명은 텍스트+이미지.
- **FR-34** 카테고리: **운영자 관리 단일 계층.** 관리자 화면에서 생성·수정·순서 변경. 판매자는 상품 등록 시 1개를 선택. 구매자 상품목록에서는 필터 탭(전체 | 카테고리…)으로 동작. 카테고리 이름은 큐레이션의 일부이므로 시스템에 하드코딩하지 않는다. (계층 구조·판매자 자율 분류는 기각)

### F4. 장바구니·주문

- **FR-14** **판매자 혼합 단일 장바구니 + 단일 주문서.** 판매자별 장바구니 분리는 명시 기각 (구매자 이탈 UX — Slur 직접 경험).
- **FR-15** 주문 내부 구조는 판매자별 하위 주문 단위로 분리 — 배송 상태가 판매자별로 독립 전이한다 (A판매자 배송중 + B판매자 배송준비 공존). 구매자에게는 하나의 주문으로 보이되 판매자별 배송 상태가 구분 표시된다.
- **FR-35** 장바구니 동작: 옵션 조합 단위로 담기(같은 조합 재담기는 수량 합산), 수량 변경, 삭제. 담기 시점에는 재고를 차감하지 않으므로 **담긴 후 품절·숨김·삭제된 항목이 반드시 발생한다** — 장바구니에서 해당 항목을 "구매 불가" 상태로 표시하고 주문서 진입 대상에서 제외한다. 주문 생성 시점에 전 항목의 재고·판매상태를 재검증하고, 실패 항목이 있으면 주문을 생성하지 않고 어떤 항목이 문제인지 알려준다.
- **FR-16** 주문서: 배송지 입력(우편번호 검색 — 검색 제공자는 아키텍처 단계에서 결정), 배송 요청사항, 결제 금액 요약(상품 합계 + 배송비 + 도서산간 추가비).
- **FR-17** 배송비는 판매자 설정: 무료 또는 유료 + 제주·도서산간 추가 배송비. 배송지 우편번호로 도서산간 여부 자동 판정.
- **FR-18** 주문 상태 전이:

```
[입금대기] ──관리자 입금확인──▶ [결제완료] ──▶ [배송준비] ──▶ [배송중] ──▶ [배송완료]
     │
     ├─ 주문 후 3일 내 미입금 → 자동취소
     └─ 구매자 자유취소: 판매자 묶음 단위, 해당 묶음이 배송준비 진입 전까지. 이후 취소·환불은 관리자 수동 처리
```

- **FR-19** 상태 전이 규칙은 FastAPI가 강제한다 — 정의되지 않은 전이는 어떤 클라이언트에서도 불가능해야 한다.
- **FR-20** `구매확정` 상태는 값만 정의하고 v1 미사용 (PG·정산 도입 시 활성화).
- **FR-21** `[ASSUMPTION]` 배송중 전이 시 판매자가 택배사+송장번호를 입력하고, 구매자 주문상세에 표시된다 (배송 추적 API 연동은 v1 제외, 송장번호 텍스트 표시까지만).

### F5. 구매자 주문 조회

- **FR-22** 주문내역 목록(최신순) · 주문상세(판매자별 배송 상태, 배송지, 금액 내역, 입금 안내 계좌).
- **FR-23** 입금대기 상태의 주문에 입금 안내(금액·계좌·기한) 표시. `[ASSUMPTION]` 계좌 정보는 관리자가 설정하는 플랫폼 단일 계좌 (내부 테스트 전용이므로).

### F6. 판매자 화면

- **FR-24** 판매자 대시보드: `[ASSUMPTION]` 처리해야 할 일 중심 최소 구성 — 신규 주문(결제완료) 건수, 배송준비 중 건수, 품절 임박(재고 5 이하 — 상수, v1은 코드 수정으로 조정) 상품. 매출 통계·차트는 v1 제외.
- **FR-25** 주문관리: 자기 상품의 주문 목록·상세 조회, 배송준비→배송중(송장 입력)→배송완료 상태 처리.
- **FR-26** 상품관리: 자기 상품 목록·등록·수정·상태 전환 (F3 참조).

### F7. 관리자 화면

운영 원칙: 초청제가 이미 품질 게이트이므로 시스템 게이트는 최소로 둔다. 기능은 필요가 확인되면 추가한다.

- **FR-27** 입점 관리: 신청 목록·상세, 승인/반려 (F2 참조).
- **FR-28** 입금 확인: 입금대기 주문 목록에서 수동 확인 → 결제완료 전이 (PG 도입 시 자동화로 대체).
- **FR-29** 주문 관리: 전체 주문 조회·검색, 상태 강제 변경 + 관리자 메모 (배송준비 이후 취소·환불의 처리 수단).
- **FR-30** 상품·회원·판매자 관리: 목록·검색·상세 조회 (읽기 중심. 제재·강제 숨김은 v1 제외).

### F8. 법적 고지·정책 (통신판매중개자 의무 — `research-market.md` §4)

- **FR-31** 푸터: 사업자 정보 + "통신판매중개자이며 거래 당사자가 아님" 고지.
- **FR-32** 중개자 고지는 푸터만으로는 부족하다 — **상품상세와 주문서에서 청약 전에** 중개자 지위와 판매자 신원정보(상호·대표자·사업자등록번호·통신판매업 신고번호·주소·연락처)가 구매자에게 노출되어야 한다. `[ASSUMPTION]` 상품상세 내 "판매자 정보" 접이식 영역 + 주문서 하단 고지 문구로 구현.
- **FR-33** 이용약관 · 개인정보처리방침 페이지. `[ASSUMPTION]` 초안은 표준 템플릿 기반으로 작성하되, **실서비스 오픈 게이트에서 법률 검토** (2025년 전자상거래법 개정으로 플랫폼 책임 강화 — 오픈 전 확인 필수).

## 6. 비기능 요구사항

- **NFR-1** 모든 권한·비즈니스 로직·상태 전이는 FastAPI 한 곳에 모은다. Flutter·Next.js는 FastAPI API만 호출하고, Supabase의 Auth·RLS·Edge Functions는 사용하지 않는다. Supabase는 매니지드 Postgres + Storage로만 쓴다.
- **NFR-2** 인증: JWT(FastAPI 발급) + Argon2id. access token 단기 + refresh token(서버 저장) 방식 — 아키텍처 스파인에서 확정.
- **NFR-3** 재고 차감·상태 전이는 동시 요청에도 정합성이 깨지지 않아야 한다 (DB 수준 원자성).
- **NFR-4** `[ASSUMPTION]` 성능 목표는 소규모 실서비스 기준의 상식선 (특별한 트래픽 요구 없음 — 별도 수치 목표를 두지 않는다).
- **NFR-5** `[ASSUMPTION]` 개인정보 최소 수집·보관: 수집 항목은 FR-4·FR-5의 최소 구성을 유지하고, 결제·정산 관련 정보는 PG 도입 전까지 수집하지 않는다.
- **NFR-6** 배포: Railway (FastAPI + Next.js). CSS는 슬러 시스템(구현 시 별도 스킬 적용).

## 7. 작업 규칙 (브리프 승계)

- **ERD(DB 스키마)는 AI가 단독 확정하지 않는다.** 초안 제시 → Slur 승인 후 진행. 마이그레이션 작성 전에도 동일.
- 화면 목록 밖 기능은 임의 추가하지 않되, 필요해 보이면 근거와 함께 제안한다.

## 8. 실서비스 오픈 게이트 (v1 완성 ≠ 오픈)

v1 코드 완성 후, 실제 구매자를 받기 전에 갖춰야 할 것들:

1. **PG 연동** (결제 자동화 + 수수료·정산·배송비 지원 설계 재논의)
2. **약관·개인정보처리방침 법률 검토** (FR-33)
3. **사업자 측 신고**: 통신판매업 신고 등 `[ASSUMPTION]` — 오픈 준비 시점에 목록 확정
4. 판매자 5~10팀 확보 — 현재 초청 가능 판매자 약 2팀(불확실, 브리프 시점). 개발과 병행하는 첫 과제 (브리프 리스크 2)

## 10. 용어

ERD·아키텍처 설계 시 명사 해석의 기준이다. 표기는 본문과 동일하게 유지한다.

| 용어 | 정의 |
|---|---|
| 조합 (variant) | 옵션값의 조합 = 구매·재고의 최소 단위. 옵션 없는 상품도 조합 1개를 가진다 (FR-9) |
| 상품 상태 | 상품 단위의 판매중/품절/숨김 3단계 — 판매자가 전환 (FR-12) |
| 조합별 판매상태 | 조합 단위의 판매 가능 여부 — 재고 0 자동 품절 + 수동 품절 토글 (FR-10). **관계**: 상품이 숨김이면 전 조합 비노출. 상품이 판매중이어도 모든 조합이 품절이면 그 상품은 구매 불가(품절 표시)다 |
| 하위 주문 | 하나의 주문 안에서 판매자별로 갈라지는 배송·상태 관리 단위 (FR-15). 구매자에게는 주문 하나로 보인다 |
| 역할 (Role) | 한 계정에 붙는 권한 묶음 — 구매자/판매자/관리자, 중복 보유 가능 (FR-3) |
| 오픈 게이트 | v1 코드 완성과 실서비스 오픈 사이에 반드시 통과해야 하는 조건 목록 (§8) |
| 초청·승인제 | 심사가 시스템 밖(초청 전 오프라인)에서 끝나는 입점 방식. 신청 폼은 심사서가 아니라 온보딩 서류다 (F2) |
