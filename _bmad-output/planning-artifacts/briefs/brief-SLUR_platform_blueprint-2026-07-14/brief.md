# SLUR 커머스 플랫폼 1호 — 프로덕트 브리프

> 독자는 Slur와 AI뿐이다. 설명보다 결정을 우선해 압축 기술한다.

> **[2026-07-21 정정]** 본 브리프의 "구매자 (Flutter, 모바일 퍼스트)"는 Slur의 원 의도(모바일 퍼스트 **반응형 웹**)와 다르게 굳은 표현이다. 구매자 표면은 Next.js 반응형 웹 PWA로 확정 전환됐다 — `_bmad-output/planning-artifacts/sprint-change-proposal-2026-07-21.md` 참조. 아래 본문의 Flutter 서술(14·26·38·56·60행)은 **당시 기록으로 보존**하며 현행 아님. 현행 표면·화면 목록의 정본은 PRD(`prds/prd-SLUR_platform_blueprint-2026-07-14/prd.md`) §1·§3·§4다.

## 1. 한 줄 정의

운영자가 판매자를 직접 선별·초청하는 **큐레이션형 디자인 편집숍 마켓플레이스** (통신판매중개자 모델). 구매자는 모바일 앱, 판매자·관리자는 PC 웹.

## 2. 목표와 성공 기준

- **1차 목표: 실서비스를 끝까지 만들어 운영해본다.** 매출·사용자 수는 1차 성공 조건이 아니다. 기능 추가 욕심이 생기면 "완주에 기여하는가"로 판정한다.
- **2차 목표: 완성 후 이 프로젝트에서 범용 커머스 플랫폼 블루프린트를 추출한다.** 여기서 내린 결정들이 다음 플랫폼의 시작 문서가 된다. (원래 이 프로젝트의 출발 아이디어였고, "백지에서 설계"가 아니라 "실물에서 추출"로 방향 전환함)

## 3. 사용자

| 사용자 | 누구 | 접점 |
|---|---|---|
| 판매자 | 소상공인 (디자인 소품·굿즈 등 "결에 맞는" 브랜드/작가) | Next.js PC 웹 |
| 구매자 | 여성 비중 높음 (확정) | Flutter 모바일 앱 |
| 관리자 | 운영자(Slur 측) — 입점 승인·회원/판매자/상품/주문 관리 | Next.js PC 웹 (판매자와 동일 앱, Role 분기) |

**입점은 초청·승인제.** 무분별하게 받지 않고 운영자가 선별해 플랫폼의 결을 유지한다. 입점 승인 화면은 관리 기능이 아니라 브랜드 전략의 도구다.

## 4. 핵심 리스크 · 열린 질문

1. **구매자가 기존 채널(29CM·아이디어스·오늘의집 등) 대신 이 앱을 쓸 이유가 아직 없다.** 유력 가설은 "여기서만 파는 독점 상품" (미감/큐레이션만으로는 기존 강자를 못 이긴다). 입점 초청 조건에 독점 상품을 거는 방식으로 큐레이션 전략과 결합 가능 — 단, 아직 검증 안 된 가설이다.
2. **판매자 파이프라인이 얇다.** 현재 초청 가능 판매자 약 2팀(불확실). 판매자 확보는 개발과 병행할 오픈 전 첫 과제. 1차 오픈 구색 기준: 판매자 5~10팀 (확정).

## 5. 범위 (화면 목록)

**구매자 (Flutter, 모바일 퍼스트)**: 로그인 · 회원가입 · 상품목록 · 상품상세 · 장바구니 · 주문서(배송지 입력) · 주문내역 · 주문상세

**판매자·관리자 (Next.js PC 웹, 단일 앱 Role 분기)**: 입점 신청 · 판매자 대시보드 · 상품관리(옵션 입력 표) · 주문관리 · 관리자 화면(입점 승인, 회원/판매자/상품/주문 관리)

**공통 필수**: 이용약관 · 개인정보처리방침 · 푸터(사업자 정보 + 통신판매중개자 고지)

### 범위 원칙

- **위 화면 목록이 v1의 기준선이다.** 목록에 없는 기능(리뷰, 검색, 알림 등)은 금지가 아니라 "아직 필요가 확인되지 않은 것" — 필요가 확인되면 그때 넣는다. 반대로 필요 없는 것을 미리 만들지 않는다(오버엔지니어링 금지). AI는 목록 밖 기능을 임의로 추가하지 않되, 필요해 보이면 근거와 함께 제안한다.
- **PG 결제·정산은 이후 단계로 미루기로 확정.** 1차 오픈은 무통장입금/외부 처리, 시스템은 주문 접수까지만 담당. 단, 주문 상태 전이에 "입금 확인" 단계를 넣어 나중에 PG를 끼울 자리를 마련해둔다.

## 6. 기술 스택 (확정)

| 구성 | 기술 | 역할 |
|---|---|---|
| 백엔드 | FastAPI (Python) | **유일한 문지기.** 인증(JWT+Argon2id — 당초 bcrypt, 2026-07-15 교체), RBAC, 상태 전이, 주문 로직 전부 소유 |
| DB·저장소 | Supabase | 매니지드 Postgres + Storage(상품 이미지)로만 사용 |
| 판매자·관리자 | Next.js | PC 웹 |
| 구매자 | Flutter | 모바일 앱 |
| CSS 방법론 | 슬러 시스템 | Next.js 스타일 규칙. 구현 시작 시 별도 문서/스킬 제공 예정 |
| 배포 | Railway | FastAPI + Next.js 호스팅 |

**아키텍처 원칙: 모든 권한과 비즈니스 로직은 FastAPI 한 곳에 모은다.** 흔한 "Supabase 풀스택"(클라이언트가 Supabase 직접 호출) 패턴을 의도적으로 배제한 결정이다. Flutter·Next.js는 FastAPI API만 바라보고, Supabase의 Auth·RLS·Edge Functions는 쓰지 않는다.

## 7. 작업 규칙

- **ERD(DB 스키마) 설계는 반드시 Slur와 논의해 확정한다.** AI가 단독으로 스키마를 확정하지 않는다 — 초안을 제시하고 승인 후 진행. 마이그레이션 작성 전에도 동일.
