# Epic 7 초안: PG 연동과 정산 (오픈 게이트)

> **상태: 초안 — 견적·PG사 선정 전 확정 금지.** 벤더 중립 설계만 담는다. 벤더 확정 후 이 문서를 epics.md에 정식 Epic 7로 이관하고 스토리 파일을 만든다.
> 근거: PRD §"실서비스 오픈 게이트"(43~44행)·FR-20·FR-23·FR-28·NFR-5, 스파인 Deferred(전이 주체만 교체), `open-gate-pg-brief-2026-07-20.md`(방향 승인 2026-07-20).

> **[2026-07-21 순서 역전] Epic 8(구매자 반응형 웹)이 Epic 7(PG)보다 선행한다.**
> 근거: `sprint-change-proposal-2026-07-21.md` §3.5 (구매자 표면을 Flutter 앱 → Next.js 반응형 웹으로 전환, 승인).
> PG 연동은 백엔드(웹훅·전이·정산)만의 일이 아니다 — **결제창 호출·인증 복귀·실패 처리·재시도가 전부 클라이언트 표면에 종속된다.** 웹 결제 플로우가 없는 상태에서 PG를 붙이면 붙이는 대상이 곧 제거될 Flutter 앱(Story 8.8)이 된다.
> Epic 7은 현재 **견적 대기(A-E456-3)** 로 아직 착수 전이므로 이 순서 변경에 **일정 손실이 없다.** 오히려 벤더의 웹 결제(리다이렉트/팝업) 방식이 앱 방식(딥링크·앱스킴 복귀 처리)보다 단순해 Epic 7 자체가 가벼워진다.
> **전환의 영향은 스토리 7.4 하나에 갇힌다** — 벤더 중립 설계 D1~D4(도메인 경계·상태 매핑·데이터 모델·멱등/보안)와 나머지 스토리 분해는 클라이언트 종류에 의존하지 않으므로 그대로다.

## 에픽 목표

무통장입금(관리자 수동 확인)을 PG 자동 승인으로 대체하고, 판매자 정산을 지급대행으로 처리해 **실구매자를 받을 수 있는 상태**가 된다.

## 벤더 중립 설계 (견적과 무관 — 지금 확정 가능)

### D1. 결제 도메인 경계

- 신규 도메인 패키지 `app/payments/` (router·service·models·schemas) — 스파인 AD-2 그래프에 `orders → payments` 또는 `payments → orders` 중 **하나만** 추가 (권장: `payments → orders` — 결제가 주문 상태를 바꾸는 방향, admin→orders 선례와 동형). 확정은 벤더 선정 시 AD-9/스파인 개정 절차로.
- **전이 엔진 불변**: 승인 웹훅은 `transition(order→paid, actor_role=system, actor_user_id=None, note="PG 승인 {거래키}")` 호출 한 줄. 연쇄 preparing·이벤트·paid_at 전부 기존 엔진 소유 (4.3). **재구현 절대 금지.**

### D2. 상태 매핑 (전이표 변경 없음)

| PG 이벤트 | 처리 |
|---|---|
| 결제 승인(카드·간편) | `pending_payment→paid` (system) |
| 가상계좌 발급 | 상태 변화 없음 — 계좌 정보만 저장·안내 (현 `deposit_account` 안내를 대체) |
| 가상계좌 입금 완료 | `pending_payment→paid` (system) |
| 결제 실패·미입금 만료 | 상태 변화 없음 — 4.5 자동취소가 기존대로 처리 (기한 소스만 PG 만료로 정렬 검토) |
| 결제 취소·환불 완료 | **역방향 전이 도입 여부 결정 필요** (4.3 defer "역방향 전이" 재개 지점) — 현 전이표엔 paid→canceled 없음. 후보 ① 라인 취소(기존 admin 경로) + 환불 기록(`refunded_at`) ② `paid→canceled` 전이 신설 |

### D3. 데이터 모델 초안 (AD-9 게이트 — 승인 필요)

| 테이블 | 목적 | 핵심 컬럼 |
|---|---|---|
| `payments` | 주문↔PG 거래 대응 | order_id FK, provider, provider_tx_id(UNIQUE), method(card/vbank/easy), amount, status(ready/paid/canceled/failed), approved_at, raw_payload(JSONB) |
| `payment_events` | 웹훅 원본 감사 (멱등 판정) | payment_id, event_type, provider_event_id(UNIQUE — 재전송 멱등), payload(JSONB), received_at |
| `settlements` | 판매자 지급 기록 | sub_order_id FK, seller_id, gross_amount, fee_amount, net_amount, status(pending/requested/paid), paid_at, provider_payout_id |

`orders`는 무변경 (금액은 계속 스냅샷 파생). `settings`의 `deposit_account`는 가상계좌 도입 후 표시 우선순위 하향(삭제 아님 — 폴백).

### D4. 멱등·보안 (웹훅의 본질적 요구)

- **서명 검증 필수** (벤더별 방식) — 실패 시 401, 본문 처리 금지
- **멱등 키**: `payment_events.provider_event_id` UNIQUE — 재전송/중복 웹훅은 INSERT 충돌로 조용히 성공 반환 (200)
- **금액 대조**: 승인 금액 ≠ 주문 활성 총액이면 `paid` 전이 금지 + 관리자 알림 대상 기록 (4.4 `expected_grand_total`·5.2 `price_changed` 패턴의 연장)
- 웹훅 엔드포인트는 인증 미들웨어 예외 + 서명 게이트 (R7 판정 규칙의 명시적 예외로 기록)

### D5. 예상 스토리 분해 (견적 후 확정)

1. **7.1** 결제 도메인·데이터 모델 (AD-9 게이트) + 벤더 SDK 배선·설정
2. **7.2** 결제 요청·승인 웹훅 (카드) — 멱등·서명·금액 대조, 전이 엔진 호출
3. **7.3** 가상계좌 (발급·입금 웹훅) — 무통장 UX 대체, 4.5 자동취소 기한 정렬
4. **7.4** **웹 결제 플로우** (`/checkout` → 결제 인증 → `/orders/complete`), 실패·취소·중복 복귀 UX — 상세 **D7** (2026-07-21 재작성)

### D7. 7.4 웹 결제 플로우 상세 (2026-07-21 재작성)

> 기존 `7.4 Flutter 결제 플로우`를 대체한다. 구매자 표면이 반응형 웹으로 확정되어 대상 화면·인증 경로·복귀 처리가 전부 바뀌었다.
> 화면 계약의 소유자는 UX 산출물이다 — `ux-designs/ux-SLUR_platform_blueprint-2026-07-21/EXPERIENCE.md`(동작)·`DESIGN.md`(시각). 이 문서와 충돌하면 **그쪽이 이긴다** (AD-14).

#### 대상 화면

| 단계 | 라우트 | 지금(v1 무통장) | PG 도입 후 |
|---|---|---|---|
| 주문서 | `/checkout` | 결제 수단은 무통장입금 하나, `주문하기` → 주문 생성 | 결제 수단 선택 추가, `주문하기` → 주문 생성 → **결제 인증 진입** |
| 결제 인증 | (PG 결제창) | 없음 | 리다이렉트 또는 팝업. 브라우저가 잠시 SLUR를 떠난다 |
| 주문완료 | `/orders/complete` | 입금 안내 상자가 화면의 중심 | 승인 결과에 따라 `결제 완료` 요약 또는 가상계좌 안내 |
| 주문상세 | `/orders/[id]` | 입금대기면 입금 안내 상자 상단 고정 | 결제 수단·승인 시각 표시, 입금대기가 아니면 안내 상자 없음 |

**주문 생성은 결제보다 먼저다.** 기존 4.4 경로(장바구니 → 재검증 → `pending_payment` 주문 생성)는 그대로 두고, 결제는 **이미 만들어진 주문에 붙는다** (D3 `payments.order_id` FK). 이 순서 덕분에 결제 도중 브라우저가 이탈해도 주문번호라는 복귀 기준점이 남는다.

#### 인증·시크릿 경로 (AD-14 준수)

**토큰·시크릿은 브라우저에 내려가지 않는다.** 구매자 웹은 판매자·관리자와 동일한 BFF 경로를 쓴다 — 브라우저는 httpOnly 쿠키만 갖고, Next.js Route Handler가 FastAPI에 중계한다 (`apps/web/lib/auth.ts`의 `proxyWithRefresh` 패턴).

```
브라우저 → [Next.js Route Handler]  → FastAPI /api/v1/payments/...  → PG
          (httpOnly 쿠키 → Bearer)    (서버 보관 시크릿으로 서명)
```

- 결제 준비 요청은 BFF를 거친다. 브라우저는 access/refresh 토큰을 읽지도 저장하지도 않는다.
- **PG 시크릿 키·서명 키는 FastAPI 환경변수에만** 둔다. Next.js에도 `NEXT_PUBLIC_*`로 두지 않는다.
- 결제창 SDK가 필요하면 브라우저에 내려가는 것은 **공개용 클라이언트 키뿐**이며, 이 키로는 승인이 일어나지 않는다.
- `[ASSUMPTION]` 벤더별 키 구분 명칭(클라이언트 키/시크릿 키), SDK 로딩 방식, 결제 준비 API의 실제 엔드포인트명은 벤더 확정 후 채운다. 위 표기는 역할 설명이지 벤더 API 이름이 아니다.
- **승인의 진실은 웹훅(7.2)이 소유한다.** 결제창에서 돌아온 브라우저의 성공 파라미터로 `paid`를 만들지 않는다 — 브라우저 복귀는 안내용이고, 상태 전이는 서명 검증된 웹훅에서만 일어난다 (AD-1·D4의 연장).

#### 폭별 동작 (EXPERIENCE.md `Responsive & Platform`)

| | < 768 (모바일 브라우저) | ≥ 768 (2단) |
|---|---|---|
| 주문서 배치 | 1단 스크롤 + 하단 고정 CTA `121,000원 · 주문하기` | 좌: 배송지·수단 / 우: sticky 요약 칼럼 안 CTA |
| 결제창 호출 | **전체 화면 리다이렉트 권장** — 모바일 브라우저는 팝업 차단·백그라운드 탭 복귀가 불안정하다 | 팝업 허용. 단 **차단 시 리다이렉트로 폴백**한다 |
| 결제 후 복귀 | 같은 라우트로 리다이렉트 복귀 | 팝업 종료 후 부모 창 갱신, 리다이렉트 폴백이면 라우트 복귀 |
| 우편번호 검색 | 전체 화면 오버레이 | 가운데 모달 |

- **같은 HTML·같은 라우트다.** 서버가 기기를 판별해 분기하지 않는다 (AD-14).
- **결제창을 다녀와도 입력이 살아 있어야 한다.** 배송지·요청사항·선택한 결제 수단이 복귀 후 초기화되면 안 된다. 주문이 결제 전에 이미 생성돼 있으므로, 복귀 화면은 로컬 폼 상태가 아니라 **주문번호로 서버를 다시 읽어** 복원하는 것을 기본으로 한다.
- 법적 고지(중개자 고지)는 결제 수단 UI가 들어와도 **`주문하기` 직전 자리를 유지**한다 — "청약 전에 읽을 수 있어야 한다"는 규제 요건이며 폭과 무관하다 (EXPERIENCE.md 법적 고지 배치 규칙).

#### v1 무통장입금 화면과의 관계

EXPERIENCE.md의 `입금 안내 상자`는 **주문완료·주문상세(입금대기)** 에 뜨고 *입금대기가 아닌 주문에서는 사라지는* 컴포넌트다. PG 도입은 이 규칙을 바꾸지 않고, **어떤 주문이 입금대기에 머무는지**를 바꾼다.

| 결제 수단 | 상태 흐름 | 입금 안내 상자 |
|---|---|---|
| 카드·간편결제 | 승인 웹훅으로 `입금대기 → 결제완료`가 **즉시 자동** (관리자 수동 확인 제거) | **뜨지 않는다.** 주문완료 화면의 중심이 입금 안내에서 결제 완료 요약(금액·수단·승인 시각)으로 바뀐다 |
| 가상계좌 (7.3) | 발급 시 상태 변화 없음 → 입금 웹훅에서 `입금대기 → 결제완료` (D2) | **남는다.** 자리·규칙은 동일하고 **데이터 출처만** 교체 — 고정 계좌(`settings.deposit_account`)·수기 안내 → 주문별 발급 계좌·PG 만료시각 |
| 무통장입금 (현행) | 관리자 수동 확인(5.2) | 폴백으로 남길지는 **7.7에서 결정** (D3의 `deposit_account` 표시 우선순위 하향과 같은 결정) |

- 주문서의 현행 문구 `결제 수단은 무통장입금 하나뿐` 및 `주문 후 3일 안에 입금하지 않으면 자동 취소됩니다.` 는 수단 선택 UI 도입과 함께 재작성 대상이다. 자동취소(4.5) 기한 안내는 **가상계좌 만료시각과 어긋나면 안 된다** (D2의 "기한 소스 정렬 검토"가 여기서 화면에 드러난다).
- `[ASSUMPTION]` 노출할 결제 수단 목록은 벤더 계약에 따라 결정된다.
