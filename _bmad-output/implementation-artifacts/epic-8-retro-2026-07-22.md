## 잘된 것

1. **AD-1(FastAPI 단일 소유)이 표면 전면 교체의 비용을 표현 계층에 가뒀다.** 구매자 표면을 통째로 다른 기술로 바꿨는데 ERD 0건·신규 API 0건·`apps/api` diff 0건이다. 코스 코렉션 제안서 §3.1이 예측한 그대로였고, 7개 스토리가 전부 `git diff --stat`으로 이를 증명했다. **"인증·상태 전이·주문 로직은 클라이언트가 아니라 서버가 갖는다"는 결정이 1년치 재작업을 막았다** — 이 회고에서 가장 값이 큰 사실이다.
2. **8.1의 세션 판정 한 줄이 8.2의 회귀 위험을 0으로 만들었다.** `middleware.ts:15`의 `role !== undefined`는 값 목록이 아니라 존재 여부만 본다. 그래서 8.2가 역할 쿠키를 `admin|seller|none` → `admin|seller|buyer`로 넓혔는데 **`middleware.ts` diff가 0줄**이다. 제안서 §3.4가 "판매자·관리자 회귀의 유일한 지점"으로 지목한 자리인데, 회귀할 코드 자체가 없었다. 잔존 `slur_role=none` 쿠키가 `buyer`와 동일 취급되어 마이그레이션조차 불필요함도 실측했다.
3. **스코프 격리가 실제로 새지 않았다.** `--b-*` 이름공간 + `[data-surface="buyer"]`로만 선언하고 `app/styles/slur/**`는 7 스토리 내내 diff 0건. 검증도 인상이 아니라 계측이었다 — 같은 `<input>`을 두 표면에 넣고 computed 값을 읽어 구매자는 `outline: rgb(31,29,26) 2px` + `box-shadow: none`, 콘솔은 파랑 `box-shadow` 그대로임을 보였다. **`--color-focus-ring` 변수 값이 양쪽에서 동일**한 것이 "전역 토큰을 재바인딩하지 않았다"의 직접 증거다.
4. **설계 판단(D1~Dn)을 근거와 함께 남긴 방식이 실제로 재검토 비용을 줄였다.** 두 종류로 효과가 갈린다.
   - **효과 있음 — 후속 스토리가 판단을 상속했다.** 8.3 D2(공개 GET에 `proxyWithRefresh` 금지: 상품 목록 요청이 상류 401에 로그인 세션을 지운다)는 8.4~8.7이 BFF를 만들 때마다 재검토 없이 적용됐다. 8.4 D5(배지는 레이아웃 컨텍스트 하나)·8.5 D2(경합은 요청 순번)·8.6 D9(입금 상자는 복제 대신 변형 추가)도 같다.
   - **효과 있음 — "왜 안 하는가"가 기록되어 되돌리기를 막았다.** 8.7 D7(service worker 미도입)은 조건부 후속 계약까지 표로 못 박아 두어, 실기기 검증에서 무엇이 확인되면 넣을지가 정해져 있다.
   - **한계** — D절이 **코드를 안 보고 확정된 규칙**일 때는 틀렸다(8.6 D11 `formatPhone`). 아래 §어려웠던 것 3 참조.
5. **Flutter판 부채를 코드로 갚은 자리가 문서에 대응됐다.** `deferred-work.md`가 "대상이 사라져 소멸"과 "웹에서 재발할 자리"를 구분해 남겨 둔 덕에, 8.4가 낙관적 갱신을 **성공에만 재조회**로 설계해 `cart_screen.dart`의 "실패 스낵바 직후 화면 튐"을 재현하지 않았다. 실패 후 2.5초 뒤에도 오류 문장이 남아 있음을 실측했다.
6. **8.8이 구현 전에 실측으로 위험을 증명했다.** `git ls-remote --tags origin`이 **비어 있었다(원격 태그 0개)**. 8.8이 `flutter-app-final`에 대해 경고하려던 사고가 이미 다른 태그(`archive/open-gate-review-2026-07-21`, `origin/main`의 조상이 아닌 커밋 `c484141`)에서 벌어져 있었다. 스토리의 안전 순서(태그 → 푸시 → **원격 확인** → 제거)가 추측이 아니라 관측 위에 섰다.

## 어려웠던 것 / 배운 것

### 1. 문서만으로는 못 잡는 버그가 3건 나왔다 — 공통점이 있다

| 버그 | 선언·명세 상태 | 실제 |
|---|---|---|
| `globals.css`의 `html, body { overflow-x: hidden }` | 규정대로 선언, computed 값도 `position: sticky / top: 74px` | **`body`가 스크롤 컨테이너가 되어 앱 전체 sticky가 죽어 있었다.** 8.1 상단바·8.4 우측 요약도 이미 안 되고 있었다. 500px 스크롤 후 sticky 요소 top이 `-500` |
| `format.ts`의 `formatPhone` | 8.6 D11이 "10자리 → 3-3-4, 예외 없음"으로 **명시 확정** | `0212345678` → `021-234-5678`. 가장 흔한 서울 번호가 가장 이상하게 나온다 |
| `lib/auth.ts`의 `clearSessionCookies` | 두 path의 refresh 쿠키를 지우도록 작성 | `ResponseCookies`가 **이름만으로 키를 잡아** 두 번째 호출이 첫 번째를 덮어썼다. `Path=/api`의 진짜 refresh 쿠키가 14일 살아남았다. **첫 수정(`set` 사용)도 같은 함정에 빠져 재수정** |

**공통점 셋.**
- 셋 다 **선언·명세는 내부적으로 정합했고 모든 정적 검사를 통과했다.** `tsc`·`lint`·`build`·코드 리뷰가 볼 수 있는 층에서는 틀린 곳이 없다.
- 셋 다 **우리가 소유하지 않은 층의 런타임 규칙**과 어긋났다 — CSS 포함 블록 규칙 / 한국 번호 체계 / Next `ResponseCookies`의 키 정책. 우리 머릿속 모델은 일관됐고 그 층이 다르게 동작했다.
- 셋 다 **공용·기반 코드**에 있었다(`globals.css`·`format.ts`·`lib/auth.ts`). 어느 화면의 AC도 이 파일을 이름으로 지목하지 않는다. 그래서 화면 단위 검증이 아무리 촘촘해도 걸리지 않는다.

**앞으로 무엇을 하면 잡히는가 — 선언이 아니라 출력을 재는 것.** 실제로 잡힌 경로가 전부 그랬다: sticky는 *스크롤한 뒤* top을 읽어서, 전화번호는 *입력 도메인 5개를 열거해서*, 쿠키는 프로덕션 빌드를 띄워 *`Set-Cookie` 줄 수를 세어서* 잡혔다. 규칙으로 정리하면 —
- **공용 코드에 손대면 그 코드의 관측 가능한 출력을 최소 3개 입력에 대해 실측한다.** 순수 함수는 입력 도메인의 경계(자릿수·접두·빈값), CSS는 상호작용 후(스크롤·포커스·리사이즈) 계산값, 응답 헤더는 실제 헤더 줄.
- **"규정대로 선언했다"를 검증 결과로 쓰지 않는다.** 8.5가 우측 칼럼 sticky를 "계산값이 `sticky`"로 확인하고 넘어갈 뻔했다 — 잡은 것은 스크롤 후 좌표였다.

### 2. UX 스파인이 사실과 다르게 적혀 있던 것이 7건 — 근본 원인은 작성 순서다

| 1 | 중개자 고지 문구(축약형) | 프로덕션 가동 중인 `BROKER_NOTICE`와 다름. 스파인이 "법적 고지는 글자 그대로"라고 해놓고 의역 | 8.3 작성 |

**왜 스파인이 API 계약을 모른 채 쓰였는가.** `bmad-ux`는 PRD와 목업으로부터 실행됐고, 그 순서는 시안 3안 → 톤 선택 → 9화면 목업 전개 → 스파인 작성이었다. 즉 **스파인은 목업을 서술한 문서**이고, 목업은 화면이 어떻게 *보이면 좋은지*를 그린 것이다. `schemas.py`·`service.py`가 대화에 처음 들어온 시점은 **스토리 작성 단계**(각 스토리의 `소비하는 백엔드 API — 계약` 절)다. 그 절이 생긴 순간부터 정정이 나오기 시작했다는 것이 표의 `발견 시점` 열이다.

이것은 사람의 부주의가 아니라 **산출물 사이에 대조 단계가 없었던 것**이다. 스파인에는 "서버가 무엇을 주는가"를 확인할 자리가 없었고, 그럼에도 스파인은 서버 동작을 **사실 문장**으로 적었다(3·4·6번). 구조적 처방은 둘 중 하나다 — (a) 스파인이 서버 동작을 기술할 때 근거 `파일:심볼`을 병기하게 하거나, (b) 스파인이 그것을 아예 기술하지 않고 스토리의 API 계약 절에 위임하게 한다.

**아직 안심할 수 없는 이유**: 7건은 스토리 7개와 리뷰 1회가 *지나간 자리*에서 발견된 것이다. 스파인 전문에 대한 사실 주장 전수 대조는 하지 않았다.

### 3. 검증 수단의 공백 — 빌드가 통과하는 버그

`apps/web`에는 테스트 프레임워크가 없다. 7개 스토리가 쓴 검증 수단은 `tsc`·`lint`·`next build`·헤드리스 크롬 렌더(+CDP 계측)뿐이었다. 렌더 검증은 실제로 강력했다 — 8.3의 칩 축 어긋남, 8.4의 768~900 라벨 꺾임, 8.5의 AC 5 위반이 전부 캡처·계측에서 나왔다. 그런데 **코드 리뷰는 그 검증이 한 번도 겨냥하지 않은 것들을 찾았다.**

| 리뷰가 찾은 것 | 왜 빌드·렌더 검증이 못 잡았나 |
|---|---|
| `다시 시도`가 6곳 중 5곳에서 **아무 반응이 없었다** (`reloadKey`만 올려 오류 화면이 그대로 남음) | 오류 화면 렌더는 확인했다. **버튼을 누른 뒤의 화면**은 어느 AC도 요구하지 않았다 |
| 혼합 묶음 체크박스가 "주문에 포함"으로 **거짓 낭독** | 시각(그레이스케일·취소선)은 확인했다. 접근성 트리의 *의미*는 육안 캡처에 나오지 않는다 |
| ≥768 주문서에서 중개자 고지가 **청약 버튼 아래**(FR-32 위반) | 8.5가 "고지는 2단 아래 전체 폭"을 규정대로 구현하고 실측까지 했다. **규정 자체가 틀렸다**(스파인 정정 7번) |
| 로그인 직후 장바구니 배지가 비어 있음 | 8.7이 로그아웃 방향만 막았다. 거울상 경로를 아무도 열거하지 않았다 |
| 옵션 `구매 가능`이 입금대기 전용 액센트를 차용 | 색은 "파랑 0건"만 검사했다. **액센트의 의미론**은 검사 대상이 아니었다 |

**공통 구조: 검증이 AC 주도였다.** AC가 이름 붙인 것은 전부 정확히 계측됐다. 그러나 AC가 이름 붙이지 않은 것 — 특히 *상호작용 이후의 상태*, *접근성 트리의 의미*, *규정 자체의 타당성* — 은 계측 대상이 아니었다. **AC 주도 검증은 "AC가 빠졌다"를 스스로 찾지 못한다.**

처방은 AC를 늘리는 것이 아니라, **화면과 무관하게 항상 참이어야 하는 명제를 자동 단언으로 고정하는 것**이다. Epic 8이 이미 그런 명제를 여럿 갖고 있다 — "재시도 버튼을 누르면 화면이 바뀐다", "HTTP 코드·에러 `code` 문자열이 화면에 0건", "구매자 지면에 파랑 0건", "포커스 링은 먹색", "하단 고정 바가 Tab 순서에서 콘텐츠보다 먼저 오지 않는다". 이 다섯은 매 스토리에서 손으로 다시 확인됐고, 그중 둘은 손 검증을 통과했는데도 리뷰가 반례를 찾았다.

### 4. 로컬 백엔드를 한 번도 못 띄웠다 — 전 화면이 스텁 위에서 검증됐다

이 머신 PATH에 `uv`도 `docker`도 없다. 그 결과:

- **7개 스토리 전부가 스크래치패드 Node 스텁으로 검증됐다.** 스텁 응답 스키마는 `schemas.py`·`service.py`·`router.py`를 **읽어서 손으로 옮긴 것**이다.
- **`uv run pytest -q`는 에픽 내내 0회 실행됐다.** 모든 스토리가 이 사실을 정직하게 적었고("통과했다고 쓰지 않는다"), 백엔드 무변경은 `git diff --stat`의 `apps/api` 0건으로만 주장했다. **이 주장은 구조적으로 타당하다**(파일을 안 열었으면 동작이 안 바뀐다). 다만 `153건 통과`와 `153건 무변경`은 다른 명제이며, 에픽이 근거로 삼은 것은 후자다.

**스텁이 못 잡게 한 것.** 스텁은 우리가 *읽은 대로* 응답한다. 그러므로 잡히지 않는 것은 **읽기가 틀린 자리**다:
- 스키마 전사 오류(필드명·nullable·타입) — 실서버 응답 1회면 드러나지만 하지 못했다.
- 스키마에 안 적힌 서버 동작. 스파인 정정 3·4번(취소 창·대표 상태 파생 방향)이 정확히 이 유형이고, `service.py`를 *일부러 찾아 읽었을 때만* 발견됐다. 안 찾았으면 스텁이 잘못된 동작을 그대로 흉내 내어 화면이 "정상"으로 보였을 것이다.
- 401 → refresh 회전의 실제 왕복, 실 카카오 인가코드 왕복(**미검증**), 에러 봉투의 예상 못 한 변종.
- 프록시 뒤 동작 전부 — `assertSameOrigin`이 Railway 엣지에서 어떻게 보이는지, 쿠키 `Secure`·`SameSite` 실제 값.

즉 **스텁 검증은 "우리 이해가 맞다면 화면은 맞다"까지만 증명한다.** Epic 8의 화면 검증은 전부 이 조건부 위에 있다.

### 5. `done`이 하나도 없다 — 그리고 그것은 규율이 작동한 결과다

8.1~8.7 어느 것도 `done`이 아니다. 이유가 스토리마다 명시돼 있다: 실기 회귀(8.1 Task 9), 카카오 콘솔·Railway 변수(8.2 Task 0), 프로덕션 실데이터(8.3), 프록시 뒤 Origin 검사 실요청(8.4·8.5·8.6), 실기기 PWA 설치(8.7). **R3·R8을 지키면 이렇게 된다** — 사람이 필요한 검증을 코드 완료와 분리해 남겼기 때문에 `done`이 비어 있는 것이지, 일이 덜 된 것이 아니다.

문제는 **8.8이 이 게이트에 물려 구조적으로 착수 불가**라는 점이다(D5: 8.1~8.7 전부 `done`). 즉 사람 검증 세션 하나가 에픽 종료의 유일한 임계 경로다. 이것은 지금 상태를 정직하게 반영하지만, 검증 항목이 7개 스토리에 흩어져 있어 **무엇을 다 하면 열리는지**가 한 곳에 없다.

## 프로세스에 대하여

### 스토리 작성과 구현을 병렬로 돌린 것 (스토리 N+1을 쓰면서 N을 구현)

커밋 순서가 그대로 증거다: `8.3 작성` → `8.2 구현` → `8.4 작성` → `8.3 구현` → `8.5 작성` → `8.4 구현` → …

**득.** 스토리 작성 패스가 **구현보다 먼저 API 계약을 읽었다.** 8.5 작성이 API↔UX 어긋남 6건을 구현 착수 전에 등재했고(`deposit_account` 단일 문자열, 201 응답에 `order_no` 없음, `3일` 하드코딩, 연락처 정규식 `^\d{9,11}$` 등), 그중 연락처 정규식은 **정상 입력이 422로 튕기는 사고**를 AC 단계에서 막았다. 스파인 정정 4건도 이 패스에서 나왔다. 계약을 먼저 고정하는 것의 값은 Epic 4~6 회고의 관찰과 같다.

**실.** 스토리 N+1은 스토리 N의 **결과가 아니라 계획**을 전제로 쓰였다. 손실이 한 곳에 몰렸다 — **검증 지시(grep·AC 체크)가 상상한 코드베이스를 향해 쓰였고, 실행하면 틀렸다.**

| 스토리 | 틀린 검증 지시 |
|---|---|
| 8.1 Task 1 | "`/terms`처럼 짧은 페이지에서 푸터 확인" — `/terms`는 뷰포트를 훨씬 넘는 긴 약관이다 |
| 8.2 AC 1 | `grep '"none"'` 0건 요구 — 8.1이 만든 SVG의 `fill: "none"`이 걸린다 |
| 8.7 Task 7 | `grep '사업자등록번호'` 0건 요구 — 그것은 **라벨**이라 반드시 1건 나온다 |
| 8.7 Task 8 | `grep 'apple-mobile-web-app-capable'` — Next 16은 현행 표준명 `mobile-web-app-capable`을 낸다 |
| 8.7 AC 8 vs D6 | 같은 스토리 안에서 `/login`의 라우트 그룹을 서로 다르게 적었다(8.2가 옮긴 것을 AC가 못 따라감) |

전부 **의도는 맞고 표현이 틀린** 유형이고, 구현자가 매번 의도를 충족시키는 대체 검증을 찾아 기록했다. 병렬 진행 자체를 되돌릴 근거는 아니다 — 다만 **스토리에 적는 grep·명령은 "실행해 본 적 없는 명령"임을 전제하고, 구현자가 고칠 것을 예상해 의도를 함께 적어야 한다**(실제로 그렇게 적혀 있어서 매번 복구됐다).

### "스토리 파일이 유일한 권위" 규약은 작동했는가

구현자가 스토리를 이긴 사례가 최소 5건이다.

| 스토리 | 이긴 내용 | 근거 |
|---|---|---|
| 8.3 | 로딩을 상태 대신 파생으로 | 3.5의 선례를 따르면 lint 2 errors — 베이스라인 0을 깬다 |
| 8.5 | 표시 판정과 제출 판정 분리 | 스토리대로 하나로 두면 **스토리 자신의 AC 5를 어긴다** |
| 8.5 | 오버레이 `m_sheet`/`m_center` 변형 미생성 | 폭 전환은 CSS만으로 해야 하므로 JS로 변형을 갈 수 없다 |
| 8.6 | `formatPhone` 서울 번호 분기 | D11이 "예외 없음"으로 확정했으나 **출력이 객관적으로 틀렸다** |
| 8.7 | 메뉴 줄 타이포를 목업 13.5px 대신 `.b_control` | AC 11의 "새 px 스케일 금지"가 이긴다 |

**규약은 작동했다 — 판단이 흔들린 사례가 없고, 매번 이유가 남았다.** 다섯 건 모두 (a) 스토리 자신의 상위 규칙, (b) 도구가 강제하는 사실, (c) 객관적 오류 중 하나를 근거로 삼았다. 임의 재량으로 이긴 사례는 없다.

**그러나 정정이 스토리 본문에 반영되지 않았다.** 대부분 `Completion Notes`에만 남았고 `설계 판단(D)` 절은 옛말 그대로다. 지금 실제로 모순이 있다 — **8.6 D11은 "서울 지역번호 같은 예외는 두지 않는다"라고 적혀 있고, 같은 파일의 Completion Notes 1번은 "명세대로 구현했고 바꾸지 않았다"라고 적혀 있는데, `format.ts:68`은 `digits.startsWith("02") ? 2 : 3`으로 분기한다.** 커밋 `a12606b`이 나중에 고쳤기 때문이다. 스토리 파일을 처음 읽는 사람은 코드와 반대되는 사실을 두 번 읽게 된다.

**필요한 규약**: 스토리가 틀렸을 때 ① 구현자가 고친다(현행 유지) ② **그 자리에서 D/AC 본문을 정정하고 `[구현 중 정정 YYYY-MM-DD]` + 사유를 남긴다** ③ Completion Notes에만 적고 끝내지 않는다. 스토리 파일은 이 저장소에서 "왜 이렇게 짜였는가"의 1차 사료이고, 사료가 코드와 반대로 적혀 있으면 다음 사람이 코드를 되돌린다.
