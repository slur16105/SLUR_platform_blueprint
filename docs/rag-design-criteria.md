# RAG 설계 판단 기준

> 2026-08-04 작성. SLUR Market에 챗봇/RAG를 도입할 때의 **설계 판단 기준**과, 그 기준을 이 프로젝트에 적용했을 때 나오는 구현 패턴들을 정리한 문서다.
>
> ⚠️ **이 문서는 제안이다.** PRD 화면 목록 밖 기능이며 구현 승인을 받은 상태가 아니다. 오픈 게이트(PG 연동·사업자 실정보·법률 검토·회원 탈퇴)에는 기여하지 않는다.

## 배경

이 프로젝트의 목적은 실서비스 직접 운영보다 **"실서비스화 가능한 수준의 서비스를 만들 수 있는지 검증하는 것"** 이다. 따라서 RAG도 "돌아가게 만드는 것"이 아니라 **상황별로 바른 구조를 고르는 판단력**을 확보하는 것이 목표다.

---

## 0. 전제 — 실패는 검색에서 난다

> RAG 실패의 대부분은 "생성"이 아니라 "검색"에서 난다.

답이 이상하면 모델을 의심하게 되지만, 실제로는 **엉뚱한 문서를 찾아다 준 경우**가 압도적이다. 좋은 문서를 넣어주면 요즘 모델은 거의 틀리지 않는다.

그래서 설계의 무게중심은 **"어떤 검색이 이 데이터에 맞는가"** 이지, "어떤 LLM을 쓸까"가 아니다.

---

## 1. 판단 축 6가지

설계를 시작할 때 이 6개를 먼저 답하면 구조가 거의 자동으로 결정된다.

### ① 다 넣을 수 있나? (코퍼스 크기)

| 크기 | 답 |
|---|---|
| ~수만 토큰 | **RAG 쓰지 않는다.** 전부 캐시된 프롬프트에 넣는다 |
| 수십만 ~ 수백만 | RAG 필요 |
| 그 이상 | RAG + 계층 구조 (요약 색인 → 원문) |

**"RAG를 안 쓰는 판단"이 실무에서 가장 자주 옳고, 가장 드물게 내려진다.** 검색 단계가 없으면 검색 실패도 없다.

### ② 얼마나 자주 바뀌나?

| 변화 속도 | 맞는 구조 |
|---|---|
| 거의 안 바뀜 (약관·FAQ) | 캐시된 컨텍스트 |
| 가끔 바뀜 (매뉴얼·공지) | 벡터 색인 + 갱신 시 재색인 |
| **실시간** (재고·가격·주문상태) | **RAG 금지 → 도구 호출(API)** |

재고를 벡터 검색으로 답하면 반드시 사고가 난다. 색인은 지난 스냅샷이라 품절 상품을 "있습니다"라고 답한다. **실시간 데이터는 검색이 아니라 조회다.**

### ③ 답이 "하나"인가 "비슷한 것들"인가

| 질문 성격 | 예시 | 맞는 방식 |
|---|---|---|
| 정확한 값 하나 | "주문번호 A123 상태?" | SQL/API 호출 |
| 의미가 비슷한 것들 | "선물하기 좋은 컵" | 벡터 검색 |
| **정확한 고유명사** | "무드컬렉션 브랜드 상품" | 키워드 검색(BM25) |

세 번째를 놓치기 쉽다. **벡터 검색은 고유명사에 약하다.** 브랜드명·상품명·주문번호처럼 글자가 정확히 맞아야 하는 것은 벡터가 못 잡는다. 그래서 실무는 대부분 **하이브리드**(키워드 + 벡터)로 간다.

### ④ 틀리면 얼마나 손해인가

| 위험도 | 설계 |
|---|---|
| 낮음 (상품 추천) | 검색 결과 그대로 답변 |
| 중간 (배송 안내) | 근거 출처 표시 + "확실치 않으면 모른다고 답하기" |
| **높음 (환불 규정·금액·법률)** | **생성 금지.** 원문을 그대로 보여주거나 API 값으로만 답변 |

SLUR Market은 **통신판매중개자**라 환불·배송비 오답이 법적 문제로 간다. 금액과 기한은 챗봇이 말로 답하면 안 되고 **서버 값을 호출해서** 답해야 한다.

### ⑤ 사람마다 볼 수 있는 문서가 다른가

구매자·판매자·관리자가 같은 챗봇을 쓴다면 **검색 단계에서 권한 필터**가 들어가야 한다. 검색해온 뒤에 걸러내면 이미 유출이다.

B2B RAG를 팔 때 **가장 많이 요구받는 항목**이다.

### ⑥ 출처를 보여줘야 하나

보여줘야 한다면 **청크에 출처 메타데이터를 처음부터 붙여야** 한다. 나중에 붙이려면 색인을 다시 만들어야 한다.

## 2. 청킹 — 여기서 대부분 망한다

기본 튜토리얼의 "500자씩 자르기"는 대부분 나쁜 선택이다. 문서마다 **의미가 끊기지 않는 자연 경계**가 있다.

| 문서 | 자연 경계 | 500자로 자르면 |
|---|---|---|
| FAQ | 질문+답변 1쌍 | 질문과 답이 갈라짐 → 검색은 되는데 답이 없음 |
| 약관 | 조항 1개 | 조항 중간이 잘려 조건절만 남음 |
| 상품 | 상품 1건 | 두 상품 설명이 한 덩어리로 섞임 |
| 문의 이력 | 문의+답변 1쌍 | 질문만 검색되고 해결책이 안 옴 |

**규칙: 자르지 말고 구조를 따른다.** 데이터에 이미 경계가 있는데 글자 수로 자르는 것은 정보를 버리는 것이다.

## 3. SLUR Market에 적용 — 4가지 패턴

축들을 이 프로젝트에 대보면 서로 다른 4가지 패턴이 나온다. 각각이 다른 이유로 다른 구조를 요구하므로 학습 커리큘럼으로도 적합하다.

### 패턴 1 — FAQ·약관 봇 · "RAG를 안 쓰는 판단"

| | |
|---|---|
| 해당 축 | ①작음 ②정적 ④위험 높음 |
| 구조 | 전문을 캐시된 시스템 프롬프트에 + 금액은 API 호출 |
| 배우는 것 | 프롬프트 캐싱, 언제 RAG가 과잉인지, 안전한 실패 설계 |
| 난이도 | ★☆☆ |

**실측 근거**: `apps/web/app/(buyer)/faq/faq-content.ts` 99줄, `apps/web/app/legal/policy-docs.tsx` 199줄. 합쳐서 약 1만 토큰 — 100만 토큰 문맥 창의 1% 수준이다.

**선행 작업**: FAQ가 지금 웹에 하드코딩돼 있다(오너 결정 2026-07-30). 챗봇이 쓰려면 서버가 읽을 수 있어야 하므로 FAQ를 API로 옮기고 웹이 그것을 받아 쓰는 형태로 정리해야 한다. 두 벌이 되면 언젠가 어긋난다.

### 패턴 2 — 상품 탐색 · 하이브리드 검색

| | |
|---|---|
| 해당 축 | ②실시간 ③의미+고유명사 혼재 |
| 구조 | pgvector(의미) + 키워드 검색(브랜드·상품명) 결합 → 결과를 실시간 API로 재확인(재고·가격) |
| 배우는 것 | 하이브리드 검색이 왜 필요한지, 순위 결합(RRF), 재랭킹, 색인과 실시간의 분업 |
| 난이도 | ★★★ |

커머스 RAG의 실전 핵심. "따뜻한 느낌 머그"는 벡터가, "무드컬렉션"은 키워드가 잡는다. 둘 중 하나만 쓰면 반드시 한쪽을 놓친다.

### 패턴 3 — 문의 이력 기반 CS 지원 · 축적형 RAG

| | |
|---|---|
| 해당 축 | ①점점 커짐 ⑤권한 필요 ⑥출처 필요 |
| 구조 | `inquiries` + `inquiry_replies` → 답변 완료 시 임베딩 1건 생성 → 관리자에게 "과거 유사 문의 3건" 제시 |
| 배우는 것 | 증분 색인(전체 재색인 없이), 권한 필터, 출처 추적 |
| 난이도 | ★★☆ |

고객에게 답하는 게 아니라 **운영자를 돕는 방향**이라 위험도가 낮으면서 가치는 높다. B2B에서 가장 잘 팔리는 형태이기도 하다.

### 패턴 4 — 판매자 운영 매뉴얼 봇 · 멀티테넌시

| | |
|---|---|
| 해당 축 | ⑤판매자별 격리 |
| 구조 | 공통 매뉴얼 + 판매자 전용 문서, 검색 단계에서 `seller_id` 필터 |
| 배우는 것 | 테넌트 격리, 검색 전 필터 vs 검색 후 필터의 차이 |
| 난이도 | ★★☆ |

## 4. 기술 스택

| 항목 | 선택 | 이유 |
|---|---|---|
| 모델 | `claude-opus-5` (기본) | 비용 조정은 실측 후 판단 |
| SDK | `anthropic` (Python) | FastAPI와 같은 언어 |
| 위치 | `apps/api/app/chat/` | 새 도메인, 기존 구조(`router`/`service`/`schemas`) 유지 |
| 컨텍스트 | 프롬프트 캐싱 (`cache_control`) | 문서를 매번 재처리하지 않음 |
| 사고 | `thinking: {"type": "adaptive"}` | 도구를 쓸지 판단해야 함 |
| 벡터 저장소 | **pgvector** (Postgres 확장) | 이미 Postgres 17을 쓰고 있어 새 인프라 0 |
| 임베딩 | 별도 제공자 필요 | Claude API에는 임베딩 엔드포인트가 없다 |

### 비용 (질문 1건당, 문서 1만 토큰 캐시 기준)

| 모델 | 질문 1건 | 하루 100건 | 월(30일) |
|---|---|---|---|
| Opus 5 | 약 22원 | 2,200원 | 약 66,000원 |
| Sonnet 5 (프로모션가) | 약 9원 | 900원 | 약 27,000원 |
| Haiku 4.5 | 약 4원 | 400원 | 약 13,000원 |

캐싱을 안 쓰면 약 10배다. **캐싱이 이 설계의 핵심이다.**

모델은 실제로 두 모델에 같은 질문 20개를 돌려 답을 비교한 뒤 정한다.

## 5. 한국어 특수 사항

| 이슈 | 내용 |
|---|---|
| 임베딩 모델 선택 | 영어 벤치마크 1등이 한국어 1등이 아니다. **우리 실제 질문으로 직접 비교**해야 한다 |
| 키워드 검색 | Postgres 기본 전문검색은 한국어 형태소를 모른다. `pg_bigm`(2-gram) 같은 대안이 필요 |
| 토큰 비용 | 한국어는 영어보다 토큰이 많다. 영어 기준 계산은 과소평가 |
| 띄어쓰기 | "무드컬렉션" vs "무드 컬렉션" — 정규화 필요 |

## 6. 안전장치 (통신판매중개자 지위 반영)

| 위험 | 장치 |
|---|---|
| 없는 규정을 지어냄 | "주어진 문서에 없으면 모른다고 답하고 고객센터로 안내"를 시스템 프롬프트에 명시. 답변에 근거 링크 첨부 |
| 금액·기한 오답 | 배송비·입금기한·환불액은 **도구를 호출해 서버 값으로** 답한다. 프롬프트에 숫자를 적지 않는다 |
| 판매자 책임을 우리 책임처럼 말함 | "상품 하자·배송은 판매자 책임, 우리는 중개자"라는 지위를 프롬프트에 못박음 |
| 남의 주문 조회 | 주문 조회 도구는 로그인 사용자 본인 것만. 사용자가 준 주문번호를 믿지 않고 서버가 소유권 검사 |
| 프롬프트 인젝션 | 상품 설명·문의 본문 같은 **사용자 생성 콘텐츠는 지시가 아니라 데이터**로 취급 |
| 비용 폭주 | 회원당 시간·일 단위 질문 수 제한, 대화 길이 상한 |
| 개인정보 | 대화 로그 보관 기간·목적을 정하고 **개인정보처리방침에 반영** (수집 항목 추가는 방침 개정 사안) |

## 7. "팔 수 있는 수준"이란 — 평가를 먼저 만드는 것

대부분은 RAG를 만들고 눈으로 몇 개 돌려보고 "잘 되네" 하고 끝낸다. 그것은 팔 수 없다. 고객이 실제로 묻는 것은 **"그래서 정확도가 몇 퍼센트인데요?"** 다.

### 최소 평가 설계

```
1. 질문 30개 + 정답 문서 를 손으로 만든다   ← 만들기 "전에"
2. 검색만 따로 측정한다
     정답 문서가 상위 5개 안에 들어왔는가?  (Recall@5)
3. 답변을 따로 측정한다
     근거 문서 안의 내용만 말했는가? (환각 여부)
     모를 때 모른다고 했는가?
4. 바꿀 때마다 다시 돌린다
```

**②와 ③을 분리하는 것이 핵심.** 답이 틀렸을 때 "문서를 못 찾은 건지, 찾았는데 못 쓴 건지"를 구분할 수 있어야 고칠 수 있다.

### 팔 때 요구받는 체크리스트

| 항목 | 왜 |
|---|---|
| 정확도 숫자 | 첫 질문 |
| **모를 때 모른다고 함** | 틀린 답보다 훨씬 중요. 신뢰가 여기서 갈린다 |
| 출처 표시 | "이 답 어디서 나왔어요?" |
| 권한 격리 | 기업 고객 필수 |
| 비용 예측 | "월에 얼마 나와요?" |
| 갱신 파이프라인 | 문서 바뀌면 어떻게 반영되나 |
| 검색 로그 | 실패 분석용. 없으면 개선 불가 |

## 8. 제안하는 진행 순서

```
1. 평가셋 30문항 작성          ← 가장 먼저. 이게 있어야 나머지가 측정 가능
2. 패턴 1 (캐시 · RAG 없음)     반나절 — 기준선(baseline) 확보
3. 패턴 3 (문의 이력 RAG)       벡터 검색 첫 경험, 위험도 낮음
4. 패턴 2 (하이브리드 상품검색)  가장 어렵고 가장 값어치 있음
5. 패턴 4 (멀티테넌시)          여유 되면
```

**2번을 먼저 하는 이유**: RAG를 만든 뒤 "RAG 안 쓴 것보다 나은가?"를 비교할 기준이 필요하다. 기준선 없이 만들면 좋아진 건지 나빠진 건지 모른다. **RAG가 기준선보다 나쁜 경우가 꽤 자주 있고**, 그것을 숫자로 잡아내는 것이 실력이다.

## 요약 — 한 문장씩

- 설계 판단은 **6개 축**(크기·변화속도·정답성격·위험도·권한·출처)에서 나온다
- 실패는 검색에서 난다. **검색과 생성을 따로 측정**하라
- **자르지 말고 구조를 따르라** (청킹)
- 벡터만으로는 부족하다 — **하이브리드**가 실무 기본값
- 실시간 데이터는 **RAG가 아니라 API 호출**
- **평가셋을 먼저** 만들어라. 그것이 "팔 수 있다"의 정의다
